## 2. 既知の制約

設計上、受け入れている制約。

### 2.1 規則の範囲

| 制約 | 影響 |
|---|---|
| 実行層が検査するのは取引の送信者だけ | ETH の受け手は検査しない。登録済みの送信者は未登録アドレスに ETH を送れる |
| 代理送信の署名者を検査するのは、実行層ではなく `LedgerForwarder` | トークンと `AtomicSwap` は `LedgerForwarder` だけを信頼する。別の Forwarder を経由した呼び出しは、署名者の代理として扱われない |
| トークンは `approve` の呼び出し元を検査しない | 停止や遮断されたアドレスの `approve` は、代理送信では `LedgerForwarder`、直接送信では実行層が止める。遮断の前に与えた allowance は残るが、遮断中は `transferFrom` がトークンの検査で失敗する |
| コントラクトのデプロイを制限しない | 登録済みの送信者は、Registry を参照しない独自トークンを作れる。DevNet で送信者になるのは運営側アカウントだけ |
| 未登録アドレスの Deposit で mint された ETH は残る | 未登録アドレスが L2 に ETH を持てる。動かすことはできない |
| 顧客と他社の自己勘定の間の移転は、トラベルルールの対象外 | 他社の自己勘定あての送金には承認が要らない |
| 承認が束縛するのは当事者、トークン、金額、期限 | 電文の中身が正しいことは、チェーンでは確かめない |
| 規則の有効化前は誰でも取引できる | 初期化の間だけ。有効化は一方向 |

### 2.2 運営への依存

| 制約 | 影響 |
|---|---|
| Gateway は 1 プロセス | 止まると取引を受け付けられない。冗長化の対象は Sequencer だけ |
| Gateway が Receipt を出さずに取引を捨てても検出できない | 仕様案のとおり。受付後の並べ替えと不採用は検出できる |
| 不採用の除外は、判定区間（受付から 120 秒）のどこかで理由が成り立てば認める | 理由が成り立つまで取引を保留した場合と区別できない |
| 運営者は op-reth に直接取引を送れる | ネットワークの分離は運営者自身を止めない。順序の保証を迂回できる。監査の C6 が事後に検出する |
| demo-tools は op-reth に直接つながる | 場面 4 の直接送信のため。直接送信に使う鍵は attacker だけにする。ほかの鍵で送った取引は C6 が検出する |
| `ConsortiumSafe` は Registry の実装を差し替えられる | 規則が読むデータの意味を変えられる。2 者の承認が要る |
| 取り下げ中の申請は、取消取引が確定するまで L2 で実行できる | その間に元の操作が実行されると、申請は `executed` になる |
| op-conductor は BFT ではない | 3 台とも同じ運営者が動かす前提 |
| ブロックのガス上限に達すると、後続の取引が先に入ることがある | DevNet の取引量では起きない。起きた場合は、監査の C4 が違反として報告する |
| 対照ノードで確認できるのは、チェーンごとに最初の未登録 Deposit だけ | そのブロックで対照ノードの導出が止まる。2 回目以降のデモでは使えない |
| VASP は入金とアラートを unsafe ブロックで記録する | 再編成で消えることがある。消えた記録は無効にする（05 章 4.6）。遮断済みのアドレスは自動では戻さない |

### 2.3 鍵と個人情報

| 制約 | 影響 |
|---|---|
| 運営側と顧客の鍵を、サービスの環境変数と DB で持つ | HSM や KMS を使わない |
| 構成員 3 者の鍵を 1 つのサービスが持つ | 複数者承認は手順として再現するだけ |
| VASP の DB の個人情報は平文 | 架空の情報だけを入れる |
| 画面の認証は簡易 | メールアドレスだけでログインできる |

## 3. 対象外の項目

| 項目 | 対象外とした理由 | 進める場合に要ること |
|---|---|---|
| Fault Proof | 実行層の規則を変えたので、標準の証明プログラムと結果が食い違う | fork から kona-client をビルドして absolute prestate を作る。dispute game に設定する。op-proposer と op-challenger を動かす |
| 出金 | Output の提出が前提 | op-proposer を動かす。出金の宛先と Registry の関係を決める |
| L1 側での Deposit の制限 | 実行層の規則で足りる | OptimismPortal の許可リスト版、または `IBridgeHook` を使う。未登録アドレスの mint 自体を止められる |
| ETH の受け手の検査 | 実行層の改造が大きくなる | EVM の value 移転に検査を入れる |
| デプロイの許可制 | DevNet では送信者が運営側だけ | Registry に権限のビットを追加し、作成取引で検査する。コントラクト内からの作成は別途 |
| EIP-7702 | 委任 EOA の発信資格を決めていない | authorization の署名者も検査する |
| MEV 対策 | 仕様案で任意 | 非公開の受付とバッチ処理の検討 |
| 複数 Active Sequencer | 仕様案で任意 | 順序の合意方式から設計し直す |
| L1 既存トークンの持ち込み、CLOB | 仕様案で任意 | - |
| 実在の KYC、トラベルルール網、AML データ | モックで代替 | 外部サービスとの接続 |
| 監査 DB の長期保存と改ざん防止 | DevNet では不要 | 保存期間、WORM 相当の保護、アクセスログ |
| 受付ログと各サービスの DB のバックアップ、復旧 | DevNet では環境を作り直す | バックアップの取得、復旧の手順、復旧後に受付ログのハッシュ連鎖を続ける方法 |
| ライセンス、法務 | DevNet が目標 | - |

## 4. 仕様案との違い

「Ethereum L2 初期技術仕様案」の採用案と、この設計が違う点。

| 要件 | 仕様案 | この設計 | 理由 |
|---|---|---|---|
| 1 | 実行クライアントを特定していない | op-reth | op-geth はサポートが終了している |
| 1 | 出金と Proof の動作も確認する | Batch 公開まで | 00 章の D3 |
| 9 | 専用 PoC で改造範囲を評価する | 改造箇所を op-revm の 1 関数に特定した | ソースを読んで特定した。動作は M2 で確かめる |
| 9 | 全ユーザー取引を対象にする | 実行層は取引の送信者を検査する。代理送信の署名者は `LedgerForwarder` が検査する | 宛先と内部呼び出しまで実行層で検査すると改造が広がる。資産の検査はトークンで行う |
| 11 | オフチェーンで交換し、業務 ID を監査 DB に残す | 受取 VASP の署名付き承認を、トークンが必須にする | 承認のない VASP 間送金をチェーンが止められる |
| 13 | 凍結はトークンの Freeze / Pause が基本 | Registry の遮断を主に使う。トークンの凍結も実装する | 遮断は全トークンと取引の送信に適用される |
| 16 | Sequencer の選択ロジックを最小改造する | 改造しない。Gateway の転送順と手数料の固定で実現する | 実行層の変更を減らす |
| 22 | Relayer を独立した構成要素とする | Gateway に内蔵する | 取引の受付を 1 か所にする |
| 25 | 監査履歴の長期保存と復旧を含む | 取り込み、検索、L2 からの取り込み直しまで | DevNet では保存期間を定めず、バックアップを取らない |
| 26 | L1 の再編成と Bridge 出金も試験する | Deposit、未登録の取引、Sequencer の切替を試験する | Sepolia では再編成を起こせない。出金は対象外 |
| - | 標準ブリッジに触れていない | 規則の有効化後は使えない | 02 章 9.2 |
