# 00 概要

## 1. 目的

ledgerA は、Registry で許可されたアドレスが取引する金融向け Ethereum L2。
このリポジトリはその DevNet（開発用ネットワーク）とデモ画面を実装する。

デモで伝えることは次の 3 点。

1. ルールを守らせるのは VASP のアプリではなくチェーンである
2. ルールが守られたことを第三者が検証できる
3. 個人情報はチェーンに載らない

デモの操作手順と確認点は [09-flows.md](09-flows.md) に記載する。

## 2. スコープ

### 2.1 含むもの

| 領域 | 内容 |
|---|---|
| チェーン | OP Stack の L2 を Sepolia 上に 1 本立てる。Sequencer と Batcher を動かす |
| プロトコル改造 | op-reth に「登録済み送信者だけが取引できる」規則を追加する。L1 Deposit 経由の取引にも適用する |
| コントラクト | Registry、ステーブルコイン 2 種、トラベルルール検証、Forwarder、Atomic Swap、受付ログ、Deposit の確認用コントラクト |
| オフチェーン | 受付 Gateway、読み取り専用の RPC プロキシ、VASP サービス 2 社分、コンソーシアムサービス、Indexer、監査ツール |
| デモ画面 | ユーザー、VASP、コンソーシアム、監査者、外部者の画面と、常時表示のチェーン表示 |
| 冗長化 | op-conductor による Sequencer 3 台構成。リーダー停止時は Gateway が未取り込みの取引を再送する |

### 2.2 含まないもの

| 項目 | 扱い |
|---|---|
| Output 提出、出金、Fault Proof | L1 では Batch の公開と再導出を扱う |
| L1 既存トークンの持ち込み、CLOB | トークンは L2 で発行する。交換には署名付き Quote を使う |
| MEV 対策、複数 Active Sequencer、数秒での確定 | Sequencer の可用性と受付順を確認する |
| 収益モデル、運営形態の決定 | DevNet の対象外 |
| 実在の KYC 事業者、トラベルルール網、AML データとの接続 | モックで代替する |
| ライセンス、法務、本番運用 | 検討しない |

## 3. 決定事項

### 3.1 構成

| No. | 項目 | 決定 |
|---|---|---|
| D1 | 基盤フレームワーク | OP Stack。実行クライアントは op-reth |
| D2 | L1 | Ethereum Sepolia |
| D3 | L1 側の検証範囲 | Batch 公開まで。Proposer と Challenger は動かさない |
| D4 | 改造コードの置き場 | `ethereum-optimism/optimism` の fork リポジトリ（`kuriyosh/optimism`）の専用ブランチ。このリポジトリは参照コミットだけを持つ |
| D5 | ユーザーの秘密鍵 | VASP が預かる。VASP のバックエンドが顧客ごとの鍵を保管して署名する |
| D6 | トークン実装 | ERC-3643 のトークン側インターフェースに沿った軽量実装。本人確認の判定は Registry を参照する |
| D7 | トラベルルール | VASP をまたぐ顧客間送金は、受取 VASP の署名付き承認を必須にする。トークンコントラクトが検証する |
| D8 | 実装言語 | サービスと画面は TypeScript。コントラクトは Solidity（Foundry）。チェーン改造は Rust |
| D9 | 冗長化 | op-conductor の 3 台構成。場面 7 でリーダーの切替を確認する |

### 3.2 設計上の決定

| No. | 項目 | 決定 | 理由 |
|---|---|---|---|
| D11 | KYC 規則の検査対象 | 実行層は取引の送信者（`from`）だけを検査する。メタトランザクションの署名者は `LedgerForwarder`、資産の送り手と受け手はトークンが検査する | 発信資格と保有資格を分ける。実行層の改造を 1 関数に収める |
| D12 | Registry の置き場 | L2 の predeploy 名前空間 `0x4200000000000000000000000000000000000700` | 実行層がアドレスを定数で持てる。genesis の加工が要らない |
| D13 | 規則の有効化 | Registry のフラグが立つまでは全送信者を許可する。フラグは一方向 | Registry のデプロイと初期登録を通常の取引で行える |
| D14 | 未登録アドレスの L1 Deposit | ブロックに入るが失敗する。mint された ETH は残る | OP Stack の失敗 Deposit の規則をそのまま使う |
| D15 | 標準ブリッジ | 規則の有効化後は使えない。ETH の持ち込みは登録済み EOA が OptimismPortal を直接呼ぶ | Messenger の別名アドレスを許可すると、未登録の L1 利用者が L2 の処理を起動できる |
| D16 | 到着順 | 受付 Gateway が通番を振り、通番順に Sequencer へ直列で転送する。priority fee は 1 wei 固定 | 実効 priority fee が同じ取引を op-reth が受付順に並べる。ガス上限などの例外は 02 章 7.2 |
| D17 | 順序の検証 | 署名付き Receipt、ハッシュ連鎖、L2 上への定期コミット、監査ツールによる事後照合 | 監査者が受付順を L2 の取り込み順と照合できる |
| D18 | ガスレス | ERC-2771 のメタトランザクション。Gateway の代理送信機能がガス代を払う | 利用者アドレスに ETH を配らずに済む |
| D19 | 代理送信の配置 | Gateway に内蔵する。VASP ごとに代理送信用アカウントを分ける | 取引の受付が 1 か所になる。VASP をまたいだ順序入れ替えを監査で検出できる |
| D20 | 複数者承認 | OP Stack の genesis に入っている Safe v1.3.0 を使う。承認は `approveHash` でオンチェーンに残す | 承認者と時刻がチェーンで確認できる |
| D21 | Atomic Swap | 署名付き Quote と Swap コントラクト。全量約定のみ | 2 通貨の移転を 1 取引で確定する |
| D22 | データ可用性 | Batcher は calldata で投稿する | L1 の Batch を使って後から L2 を再構築できる |
| D23 | L1 データ手数料 | 0 に設定する。L2 の genesis と L1 の `SystemConfig` の両方で fee scalar を 0 にする。L2 の base fee は最小値まで下がる | 送信者は運営側のアカウントだけになる |
| D24 | トークンの桁 | tJPY、tUSD とも小数 6 桁 | 画面とテストの扱いを揃える |
| D25 | EIP-7702 取引 | 規則の有効化後は拒否する | 委任 EOA の発信資格の扱いを決めていない |
| D26 | アプリ層の開発 | anvil 1 台を L2 の代わりにするモードを用意する | チェーン改造と並行してコントラクトとサービスを開発できる |
| D27 | op-reth の RPC | ホストとサービスには読み取り専用の rpc-proxy だけを見せる。op-reth に取引を送れるのは Gateway と、場面 4 の demo-tools だけ | 到着順の前提（Gateway 以外から書き込めない）をネットワーク構成で担保する |
| D28 | 不採用の監査 | 発行済みの全 Receipt を期限で監視する。除外として認めるのは、監査ツールが L2 の状態で理由を確認できたものだけ | Gateway が申告する転送状態と拒否理由は、Receipt の署名対象ではない |
| D29 | 申請の取り下げ | 承認がオンチェーンにある申請は、同じ nonce の取消取引を実行して取り下げる | Safe の承認は nonce が進むまで有効 |
| D30 | デモの再演 | 登場人物と監査の集計区間を「デモ回」ごとに分ける | チェーンを作り直さずに場面 1 から再演できる |

## 4. 用語

| 用語 | 意味 |
|---|---|
| VASP | 顧客の KYC とアドレス管理を行う事業者。デモでは A 社と B 社 |
| Registry | アドレスの所属 VASP、種別、状態を持つ L2 コントラクト（`KycRegistry`） |
| 発信資格 | 取引に署名して送信できること。実行層が検査する |
| 保有資格 | トークンを保有、受領できること。トークンが検査する |
| 規則の有効化 | Registry の `enforcementEnabled` フラグを立てること。以後、未登録の送信者は取引できない |
| 受付 Gateway | 取引を受け付ける唯一のサービス。通番と Receipt を発行する |
| Receipt | Gateway が署名した受付証。通番、取引ハッシュ、受付時刻、直前のハッシュを含む |
| 代理送信 | 利用者が署名したメタトランザクションを、運営側のアカウントが L2 取引として送ること |
| 承認（attestation） | 受取 VASP が署名したトラベルルールの承認。個人情報を含まない |
| コンソーシアム | Registry の管理者。3 社中 2 社の署名で操作する Safe |
| unsafe / safe / finalized | L2 ブロックの確定段階。Sequencer が生成 / L1 に Batch 公開 / L1 で確定 |
| 失敗 Deposit | L1 から取り込まれたが実行に失敗した取引。ブロックには入り、nonce と mint だけが反映される |
| 検証ノード | 改造版の op-reth で、L1 の Batch だけから L2 を導出するノード。Sequencer と同じ判定になることを確かめる |
| 対照ノード | 標準の op-reth で、L1 の Batch だけから L2 を導出するノード。改造版と結果が違うことを確かめる |
| 取消取引 | Safe の nonce を消費するだけの取引。宛先は Safe 自身、データなし。承認済みの申請を失効させる |
| デモ回 | デモ 1 回分の区切り。登場人物のアドレスと、監査の集計を始める通番を持つ |

## 6. 既知の制約

### 6.1 規則の範囲

| 制約 | 影響 |
|---|---|
| 実行層が検査するのは取引の送信者だけ | ETH の受け手は検査しない。登録済みの送信者は未登録アドレスに ETH を送れる |
| 代理送信の署名者を検査するのは、実行層ではなく `LedgerForwarder` | トークンと `AtomicSwap` は `LedgerForwarder` だけを信頼する。別の Forwarder を経由した呼び出しは、署名者の代理として扱われない |
| トークンは `approve` の呼び出し元を検査しない | 停止や遮断されたアドレスの `approve` は、代理送信では `LedgerForwarder`、直接送信では実行層が止める。遮断の前に与えた allowance は残るが、遮断中は `transferFrom` がトークンの検査で失敗する |
| コントラクトのデプロイを制限しない | 登録済みの送信者は、Registry を参照しない独自トークンを作れる。DevNet で送信者になるのは運営側アカウントだけ |
| 未登録アドレスの Deposit で mint された ETH は残る | 未登録アドレスが L2 に ETH を持てる。動かすことはできない |
| 顧客と他社の自己勘定の間の移転は、トラベルルールの対象外 | 他社の自己勘定あての送金には承認が要らない |
| 承認が束縛するのは当事者、トークン、金額、期限 | 電文の中身が正しいことは、チェーンでは確かめない |
| 規則の有効化前は誰でも取引できる | 初期化の間だけ。有効化は一方向 |

### 6.2 運営への依存

| 制約 | 影響 |
|---|---|
| Gateway は 1 プロセス | 止まると取引を受け付けられない。冗長化の対象は Sequencer だけ |
| Gateway が Receipt を出さずに取引を捨てても検出できない | 受付後の並べ替えと不採用は検出できる |
| 不採用の除外は、判定区間（受付から 120 秒）のどこかで理由が成り立てば認める | 理由が成り立つまで取引を保留した場合と区別できない |
| 運営者は op-reth に直接取引を送れる | ネットワークの分離は運営者自身を止めない。順序の保証を迂回できる。監査の C6 が事後に検出する |
| demo-tools は op-reth に直接つながる | 場面 4 の直接送信のため。直接送信に使う鍵は attacker だけにする。ほかの鍵で送った取引は C6 が検出する |
| `ConsortiumSafe` は Registry の実装を差し替えられる | 規則が読むデータの意味を変えられる。2 者の承認が要る |
| 取り下げ中の申請は、取消取引が確定するまで L2 で実行できる | その間に元の操作が実行されると、申請は `executed` になる |
| op-conductor は BFT ではない | 3 台とも同じ運営者が動かす前提 |
| ブロックのガス上限に達すると、後続の取引が先に入ることがある | ブロック内の順序が通番と食い違うと、監査の C4 が報告する |
| 対照ノードで確認できるのは、チェーンごとに最初の未登録 Deposit だけ | そのブロックで対照ノードの導出が止まる。2 回目以降のデモでは使えない |
| VASP は入金とアラートを unsafe ブロックで記録する | 再編成で消えることがある。消えた記録は無効にする（05 章 4.6）。遮断済みのアドレスは自動では戻さない |

### 6.3 鍵と個人情報

| 制約 | 影響 |
|---|---|
| 運営側の鍵は環境変数で渡す。顧客の鍵は暗号化して VASP の DB に保存する | HSM や KMS を使わない |
| 構成員 3 者の鍵を 1 つのサービスが持つ | 複数者承認は手順として再現するだけ |
| VASP の DB の個人情報は平文 | 架空の情報だけを入れる |
| 画面の認証は簡易 | メールアドレスだけでログインできる |
